Транскрайбер «нажал Enter, сказал фразу — получил текст» для слабых машин.
Распознавание локальное через [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx)
(русская модель Zipformer int8). В отличие от groq-voice (faster-whisper
large-v3: ~3GB на диске, ~4GB RAM, долгий старт), здесь:

> Карта продукта, текущее состояние, решения и «не трогать» —
> [docs/PRODUCT.md](docs/PRODUCT.md) (живая спека: читать ПЕРВЫМ перед
> работой над проектом, обновлять после правок).

| Параметр | sherpa-voice | groq-voice (large-v3) |
|---|---|---|
| Модель на диске | **74 MB** (или 29 MB streaming) | ~3 GB |
| RAM | ~300 MB | ~4 GB |
| Старт | <1 с | 20–30 с |
| Скорость распознавания | RTF отличный (Zipformer) | на CPU медленно |
| VAD | встроен | встроен (Silero) |

Выбор решения обоснован веб-ресёрчем (08.2026, через Camoufox): для русского
на CPU без GPU sherpa-onnx с русской Zipformer int8 — лучший баланс
качество/вес; Vosk ещё легче, но качество хуже; faster-whisper small — баланс
с качеством Whisper, но тяжелее.

## Установка

> Журнал всех изменений с причинами и отвергнутыми вариантами —
> [CHANGELOG.md](CHANGELOG.md).

```bash
cd sherpa-voice
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
```

Первый запуск скачает модель (~74MB) автоматически в `models/`.

## Запуск

```bash
./run.sh                              # по умолчанию GigaAM v3 transducer (230MB, лучшее качество + hotwords)
./run.sh --model offline               # zipformer int8 (74MB)
./run.sh --model streaming             # стриминговая small (29MB, быстрее)
./run.sh --file audio.wav              # распознать файл (для тестов)
./run.sh --list-devices                # список аудиоустройств + что выбирает auto
./run.sh --device "hw:0,0"             # явное устройство (или имя из списка)
./run.sh --once                        # одна запись и выход (для хоткея)
./run.sh --silence 4                    # фоновый режим: стоп через 4с тишины (по умолчанию выкл)
./run.sh --auto-export                # каждая запись сразу в MD/PDF
./run.sh --telegram-daemon             # фоновый приём голосовых из Telegram

# или напрямую:
python transcribe.py [те же флаги]
```

Поведение: Enter → начать запись, Enter → остановить → текст в консоль +
в буфер обмена. Буфер работает честно: на Wayland нужен `wl-copy`
(`sudo dnf install wl-clipboard`), на X11 — `xclip`/`xsel`; если утилиты нет —
текст сохраняется в `~/.cache/sherpa-voice/last.txt` (с пояснением в консоли).

Текстовый ввод (вписать текст вместо Enter) обрабатывается **как запись**:
полировка → подмешка → транскрипт в Telegram (если включён) → меню действий.
Режим чата с ИИ (ответ на промпт) в текстовом вводе нет — ответ ИИ только
по кнопкам меню (1/2/4), как после голосовой записи.

## Telegram (`[6] 📨` в меню)

Дублирование результатов в Telegram-бот. Настройка — подменю `[6]`:
`[1] 🪙 Токен` (из @BotFather), `[2] 🆔 Chat ID` (число; если не знаете —
введите `?`, приложение найдёт его само по последнему сообщению боту),
`[3] 🔄 Вкл/выкл`, `[4] 📤 Отправить текст` (текущий результат вручную),
`[5] 🧪 Тест` (проверка связи), `[6] 🗑 Очистить`. Настройки хранятся в
каталоге настроек (`telegram.txt`: ON/OFF, токен, chat_id; файл с правами
`0600` — токен бота это секрет, см. «Настройки»).

Что отправляется, когда режим включён:
- после распознавания — улучшенный текст (с подмешкой) автоматически;
- саммари, ответ и кодинг-промт — сразу после генерации в меню;
- файлы экспорта (MD и PDF) — после `[3] Экспорт`.

Текст длиннее 4096 символов режется на сообщения (лимит Bot API). Бот

честно, распознавание при этом не ломается.

### Кнопки под ответом (управление из Telegram)

После транскрипции (голосовое боту или автоотправка с микрофона) под
текстом приходят inline-кнопки: **Саммари / Ответить / Кодинг-промт / Экспорт /
Документация** — те же действия, что в меню консоли, плюс кнопка
«📖 Документация» отправляет актуальный README в чат (или команда `/docs`).
Кнопки цветные (официальный `style` Bot API 9.4): Саммари и Экспорт —
зелёные, Кодинг-промт — красная, Документация — синяя; у старых клиентов
кнопки просто без цвета. Нажатие: сразу видимое
«Готовлю …», потом результат в тот же чат, кнопки остаются на новом
сообщении (цепочка действий не рвётся). Повторное нажатие той же кнопки
не дублирует запрос (защита от двойного нажатия). Экспорт уходит файлом
(MD/PDF) в тот же чат и включает сделанные саммари/ответ/кодинг-промт.
Если кнопки недоступны — текстовые команды-фолбэк: «саммари», «/export».
Значки-префиксы в сообщениях бота — жирный текст, заголовки `##` из
ответов модели тоже (Telegram их не понимает).

### Голосовые из Telegram в систему

Двусторонний мост: голосовое сообщение боту → скачивается (Bot API) →
декодируется через ffmpeg → распознаётся той же моделью → полируется через
DeepSeek → приклеивается подмешка → результат печатается в консоль и
уходит в тот же чат как **rich-сообщение** (официальные Rich Messages,
Bot API 10.1): заголовок «📝 Транскрипт», **широкая цитата** с текстом,
разделитель и цветные кнопки действий. Если rich-формат не проходит
(старый клиент или ошибка API) или текст длиннее 4000 символов — фолбэк
на обычный текст с кнопками. Работает, когда
режим Telegram включён. Пока бот обрабатывает голосовое, он «печатает»
(индикатор набора текста) и ставит на голосовое реакцию 🤔 — при готовности
меняет её на 👍, при пустом распознавании или ошибке — на 👎 (реакции —
косметика: если Telegram их не примет, транскрипция не ломается):

- **в основном режиме** — голосовые ловятся фоном, пока сидите в терминале
  (текст виден в консоли, копируется в буфер и в историю);
- **отдельным процессом** без терминала:
  `./run.sh --telegram-daemon` (в `--once` приём не запускается — одна
  запись и выход).

Текстовые сообщения боту — команды-фолбэк («саммари», «/export»), если
кнопки недоступны. Пустое распознавание не отправляется. **Один слушатель
на бота**: Telegram разрешает только один getUpdates-процесс; если
запущены два (вторая копия или демон), один получает `409 Conflict` и
понятное сообщение, что делать (закрыть лишний экземпляр и перезапустить).

## Тест полного цикла (без человека)

```bash
./venv/bin/python test_cycle.py    # 8 проверок: синтез → ASR (offline+streaming) →
                                    # полировка → меню → экспорт → буфер. Выход по exit code.
```

Речь синтезируется espeak-ng (не требует микрофона и рук). Критерий
распознавания — непустой текст: синтетика не равна натуральной речи, тест
проверяет пайплайн, а не качество ASR.

## Настройки (.env) и каталог настроек

Файл `.env` кладётся рядом со скриптом (в корень проекта), ключ вставляете
сами — не коммитьте его:

```
DEEPSEEK_API_KEY=sk-...
DEEPSEEK_MODEL=deepseek-v4-flash
DEEPSEEK_AUTO_POLISH=1
MIC_DEVICE=Встроенное аудио Аналоговый стерео
```

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `DEEPSEEK_API_KEY` | — | ключ DeepSeek: полировка, Саммари/Ответ/Кодинг-промт |
| `DEEPSEEK_MODEL` | `deepseek-v4-flash` | модель DeepSeek |
| `DEEPSEEK_AUTO_POLISH` | `1` | автоулучшение текста после распознавания (`0` — выключить) |
| `MIC_DEVICE` | — | закрепить микрофон: имя или индекс из `--list-devices` (перекрывает `auto`) |

**Каталог настроек** — `$XDG_CONFIG_HOME/sherpa-voice` (обычно
`~/.config/sherpa-voice`); если он недоступен для записи (read-only HOME),
откат на `~/.cache/sherpa-voice` с сообщением при старте. Там лежат
`mix.txt` и `telegram.txt`. Запись атомарная (temp + rename — файл не
повреждается при падении), `telegram.txt` — права `0600`. В `~/.cache`
остаются только пересоздаваемые файлы (маркеры записи, `last.txt`, история).

## Проверка микрофона

Если распознавание плохое или тишина — проверьте, какой вход реально
ловит звук (говорите в микрофон во время записи):

```bash
./venv/bin/python mic_check.py            # все входы по 3с
./venv/bin/python mic_check.py hw:0,2     # конкретный вход
```

RMS ~0.001+ = звук есть; RMS ~0 = тишина (не тот вход / микрофон muted).
На ALC887: `hw:0,0` = задняя панель (Rear Mic), `hw:0,2` = передняя
(Alt Analog). ВАЖНО: распознавание работает на 16 кГц, а `hw:*` часто
поддерживает только 48 кГц (поток не откроется — «микрофон не видит»).
Автовыбор идёт через дефолтный вход PipeWire (`default` — пересэмплит под
16 кГц; при выбранном Easy Effects Source это чистый микрофон с
шумоподавлением). Явное устройство: `./run.sh --device "hw:0,2"`.

## Грабли (проверено ресёрчем)

- **Частота** — карта ALC887 через ALSA не отдаёт 16kHz (`paInvalidSampleRate`),
  поэтому запись идёт на родных **48kHz**, а перед распознаванием ресемплит
  в 16kHz через `soxr`. sherpa-onnx ожидает ровно 16kHz.
- **Старт потока** — конструктор `sd.InputStream(...)` в sounddevice не
  запускает поток: без явного `stream.start()` callback не вызывается, и запись
  «молча» пустая. В этом проекте `start()` вызывается сразу после открытия
  (был баг «не записывает» — исправлено 08.2026).
- **Микрофон занят** — автоматические ретраи с ожиданием (устройство может
  быть занято другим приложением). Если скрипт «завис» и микрофон перестал
  работать — почти всегда виноват оставшийся процесс прошлого запуска, который
  держит вход через PipeWire (в журнале: `spa.alsa: 'front:0': capture open
  failed: Устройство или ресурс занято`):
  ```bash
  ps aux | grep transcribe.py        # найти зависший процесс
  kill <PID>                          # освободить микрофон
  ```
  С 08.2026 скрипт сам не даёт запуститься второму экземпляру (lock-файл),
  открывает микрофон по таймауту и сообщает «микрофон не отдаёт данные»
  вместо молчаливого зависания.
- **Модели** — int8-версии критичны на CPU (fp32 в 2-3× медленнее).
