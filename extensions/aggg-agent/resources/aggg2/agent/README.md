Каждый агент живёт в своей подпапке `agent/<имя>/`:

Есть: `reverser/` (реверс-инжиниринг, эталон), `semble-search/`

вызов `@zan`).

| Файл | Роль |
|---|---|
| `AGENT.md` | конфиг-точка входа: как подключить, структура, протокол работы |
| `<ИМЯ>.md` | личность агента: identity, beliefs, decision framework, anti-patterns, output |
| `skills/` | скиллы агента (стандарт Agent Skills: `SKILL.md` с frontmatter name/description) |

Правила:
- Новая способность агента = новый скилл в его `skills/<name>/SKILL.md`.
- Формат нового агента — по любому существующему в `agent/` (структура
  и стиль должны совпадать).
- Подключение к харнесу — см. `AGENT.md` конкретного агента.

## Изоляция скиллов: когда шарить, когда нет

Скиллы в `agent/<имя>/skills/` разносит `install_agents.py` в общие
каталоги харнесов — их видят ВСЕ агенты. Это НОРМА (ресёрч 13.08.2026,
Microsoft agent-skills, Claude Code 2.x):

- **Контекст не страдает** — progressive disclosure: у агента всё время
  висят только метаданные (~100 токенов на скилл; Microsoft держит 132+
  скиллов так). Полный SKILL.md грузится по триггеру.
- **Маршрутизация требует видимости** — основной агент должен видеть
  description скиллов спец-агента, чтобы знать, кого делегировать
  (пример: triage-route → субагент reverser).
- **Шумную работу изолирует субагент**, не скилл: делегирование в
  отдельный контекст (~0 токенов до вызова).

НЕ шарить (держать в приватной папке агента, вне разноса) только:
1. **Конфиденциальное** — то, что не должно попадать к получателю
   раздаваемой копии или к другим агентам.
2. **Конфликт триггеров** — description пересекается с чужим скиллом.
3. **Лишнее знание** — другим агентам не нужно знать, что так умеем.

Правило: кладёшь в `skills/` — значит ОК, что это увидит каждый агент
воркспейса **и попадёт в раздаваемую копию** (в архив входит весь
`agent/`, кроме папок, исключённых сборщиком). Конфиденциальное — НИКОГДА
не в файлах, идущих в раздачу.
