# changelog-discipline

CHANGELOG не дублирует историю версий (её ведёт VCS) — он сохраняет **решения**: почему выбрали этот путь, что было до, что отвергли. Этого в коде не найти.

## Где это нужно

- После **каждой** правки кода в проекте с changelog; при первом заведении; при релизе
- НЕ для commit message, PR-описаний и релиз-нот для пользователей

## Опорные принципы

- **Адресат — «я через полгода»**: запись самодостаточна, контекст забыт
- **«Зачем» важнее «что»**: «что» покажет дифф
- **Отвергнутый вариант — золото**: защищает от «улучшения» обратно
- **Писать сразу после правки**: отложенная запись вырождается в пересказ диффа
- **Без исключений**: одно пропущенное «мелочное» изменение = журнал выборочный, а выборочному нельзя верить

## Формат

### Скелет файла

```markdown
# Changelog

Все заметные изменения <проект>. Формат — Keep a Changelog.

---

## [Unreleased]

### Added
### Changed
### Fixed

---

## [0.1.3] — 2026-07-31

### <Заголовок релиза — одной фразой о сути>

- **Что:** …
- **Где:** …
- **Почему:** …
- **Было:** …

### Added
### Changed
### Fixed
```

### Резюме релиза: четыре поля

| Поле | Смысл |
|---|---|
| **Что** | что теперь работает иначе — на языке продукта |
| **Где** | затронутые файлы и области |
| **Почему** | какую боль снимает |
| **Было** | как было раньше — единственное место, где прежнее поведение останется зафиксированным (пропускают чаще всего) |

### Записи внутри секций

Одна запись = одно решение, не один коммит: **жирный заголовок** (суть одной фразой) + что поменялось (типы/функции) + **почему так** (если неочевидно) + **что отвергнуто и почему** (если варианты были).

Пример:

> **ПКМ вместо всплывающего меню по ховеру.** Копирование ссылки переехало в контекстное меню (`LinkContextMenu`) — до ховер-кнопки не успевал доехать курсор.

Отвергнутое + причина = защита от обратного «исправления» через полгода.

## Порядок действий

1. Сразу после правки дописать секцию в `[Unreleased]` (Added/Changed/Fixed)
2. Писать от продукта: «теперь можно X», не «добавил параметр в функцию»
3. Решение неочевидно → зафиксировать причину и отвергнутое
4. На релизе: `[Unreleased]` → версия с датой + резюме из четырёх полей

## Проверка

Запись оправдана, если через полгода отвечает: что изменилось для пользователя / почему так / где смотреть код / как было раньше. Запись, пересказывающая дифф, не нужна.

## Этапы (handoff)

- **Вход из:** `task-cycle` (фаза 7), `code-review`, любая правка кода
- **Дальше:** — (журнал закрыт); продукт знания — `wiki-karpathy`
