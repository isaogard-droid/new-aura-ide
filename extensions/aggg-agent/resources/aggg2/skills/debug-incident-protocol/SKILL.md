# Debug & incident protocol: факты до теорий, зависания

Первоисточник: `docs/patterns/GLAV-PATTERNS.md` (E 38-44, L.9-15, M.34/56); `UNIVERSAL-PATTERNS.md` — «Защита от зависаний».

## 1. Ядро: факты, не мнения

1. **FACTS BEFORE THEORIES** — порядок: config flags → DB row → log lines → код-гипотеза.
2. **SYMPTOM ≠ ROOT CAUSE** — трассируй call path до side-effect; корень чини ОДИН раз (shared function, не 10 патчей).
3. **METRIC FLAT + UX «WORKS» = SILENT FAILURE** — ищи except/early return на пути метрики.
4. **SINGLE CONSUMER FOR EXCLUSIVE STREAMS** — long-poll/queue/lock file — один владелец; health = exactly one PID.
5. **RESTART RITUAL IS PART OF THE FIX** — код на диске ≠ код в памяти; stop all → start one → verify log; PID creation time > edit time.
6. **ENCODING OF CONSOLE ≠ ENCODING OF PRODUCT** — кракозябры в консоли Windows ≠ битые данные; проверяй UTF-8 в клиенте/файле.
7. **INCIDENT CHECKLIST TEMPLATE** — повторяемые инциденты → чеклист рядом с runbook (flags? storage? logs? single instance? money path except?).

## 2. Локализация зависаний (UNIVERSAL-PATTERNS)

1. **«Не может зависнуть» — не аргумент** — зависает всё (сеть без таймаута, Read-Host, интерактив, бесконечный цикл). Доказывает только запуск с таймаутом.
2. **Маркер прогресса, не последняя строка** — маркер («=== этап N ===») в НАЧАЛЕ блока → зависло ВНУТРИ последнего блока. Нет маркеров — добавь.
3. **Прогресс — в ФАЙЛ, не в пайп** — `cmd 2>&1 | Out-File prog.txt` (пайп в tail может зависнуть/потерять хвост при kill).
4. **Изолируй подозреваемого** — один блок с малым таймаутом (30-60с), не весь набор с 900с.
5. **Сначала API инструмента** — `--help`/Get-Help; 2 неудачные попытки = минус два таймаута.
6. **A && B && C маскирует место зависания** — этапы раздельно: своя команда, свой таймаут, свой маркер.
7. **Первый подозреваемый — инфраструктура** — BeforeAll/dot-source/модули/сеть/интерактив виноваты чаще тестов.
8. **Сравни с последним успешным прогоном** — git diff: виновник обычно в изменениях.
9. **Таймаут — всегда и прогрессивный** — малый на подозреваемое; расти только если операция легитимно долгая.

## 3. Процессы (Windows/Linux)

- **PID TRACE CHAIN** — ParentProcessId → launcher → рабочий каталог.
- **LOG TIMELINE CORRELATION** — лог старше LastWriteTime файла = процесс не перезапущен.
- **STOP-ALL-THEN-START-ONE** — убить старые процессы перед стартом (два PID с одним токеном = Conflict).
- **PROCESS CREATION TIME CHECK** — CreationDate < edit time = старый код.
- **POST-RESTART LOG TIMESTAMP FILTER** — после рестарта только строки после времени старта (старый Conflict ≠ текущая проблема).
- **RESTART WITH VERIFICATION WINDOW** — Start-Sleep 12-15s → свежие строки → нет Conflict/ERROR → только тогда «готово».
- **FIRE-AND-FORGET WITH PID CAPTURE** — Start-Process -PassThru → $proc.Id → проверка жив ли.
- **PROCESS FILTER BY PROJECT PATH** — `-match 'project-name'`, НЕ `'python'` (сотни чужих).
- **GRADUAL ERROR NARROWING** — процессы → PID → CommandLine → лог → строка; фильтр на каждом шаге.
- **PRODUCTION PROCESS PRESERVATION** — Stop-Process только подтверждённым PID; production явно исключается.

## 4. Кэш и «всё ещё сломано»

- **Старый кэш = неисправленный баг** — сначала curl + grep строки-маркера правки (сервер отдаёт исправленное?), потом убить кэш: ?v=N, no-cache.
- **Чужие процессы на порту** — тестовый инстанс блокирует реальный запуск; проверь владельца порта ДО диагноза.

## 5. MCP failed при старте (гонка с монтированием диска)

- **Симптом:** при старте харнеса ВСЕ MCP с путями на внешний диск падают РАЗОМ: python — «MCP error -32000: Connection closed», скрипты — «ENOENT posix_spawn»; выживают только не зависящие от диска.
- **Корень:** харнес стартовал раньше, чем ОС смонтировала диск (udisks2 монтирует лениво при логине). Сверка: `ps -o lstart` харнеса vs `journalctl -k | grep mounted` (лог может быть в UTC).
- **Перед диагнозом:** запустить сервер РУКАМИ — отвечает на MCP initialize = сервер жив, дело в окружении старта.
- **Фикс:** перезапустить сервис харнеса (opencode: `opencode2 service restart`; ретраев MCP нет — статус failed застывает).
- **Профилактика:** fstab с `nofail` (до логина) или systemd `RequiresMountsFor=<путь>` (systemd.io: /run/media — regular mount, ordered after).
- **Грабля fstab+/run/media:** mount-юнит входит в local-fs.target, а systemd-tmpfiles-setup идёт After — `/run/media/<user>` до логина не создаётся. Фикс: drop-in с `[Mount] ExecStartPre=/usr/bin/mkdir -p /run/media/<user>`.

## 6. Capture-фаза: зафиксируй сбой ДО ретрая (AgentDebugX, affaan-m)

Слепой ретрай = второй прогон без новой информации. Перед повтором заполнить (~30с):

```text
## Failure Capture
- Задача / сессия:  - Цель:
- Ошибка (тип/сообщение/стек):  - Последний успешный шаг:
- Последняя неудачная команда/вызов:  - Повторяющийся паттерн:
- Давление контекста (повторные промпты, гигантские вставки):  - Допущения окружения (cwd, ветка, сервис, файлы):
```

Правило: 2+ ретрая без новой информации — стоп, зафиксировать, сменить подход.

## 7. Застревание: Repeater / Wanderer / Looper (agentpatterns.ai)

| Форма | Симптом | Лечение |
|---|---|---|
| **Repeater** | тот же шаг/вызов снова | стоп: что изменилось? Ничего — сменить подход |
| **Wanderer** | дрейф «похож на дело», но от цели | вернуться к формулировке, перепланировать |
| **Looper** | цикл 2-3 шагов, прогресса нет | разорвать: новая информация или эскалация |

Разделитель «застрял vs медленно» — метрика прогресса (продвижение к цели), не число вызовов.

## 8. Лестница восстановления (nudge → replan → escalate → reset → hand-off)

1. **nudge** — перечитать ошибку, маркер прогресса. 2. **replan** — другая гипотеза/инструмент/порядок. 3. **escalate** — доки/первоисточники, субагент-ресёрч, skills_search.py «симптом». 4. **reset** — новый контекст/сессия без старых допущений (Capture сохраняет факты). 5. **hand-off** — человеку: факты, что пробовал, гипотезы. Эскалация — штатная ступень.

## 9. ACH: ≥2 конкурирующие гипотезы, refute-first (Heuer)

Многофакторный инцидент → ≥2 гипотезы, для каждой — ЧТО ЕЁ ОПРОВЕРГНЕТ; проверять опровержения, не подтверждения (защита от confirmation bias; эмпирика слаба: Dhami 2019). Быстрые инциденты с очевидным корнем не тащить.

## Workflow (порядок применения)

1. Факты (config flags → DB row → log lines → код); Capture до ретрая; исключи кэш (curl + grep маркера) и чужие процессы на порту.
2. Симптом vs корень — один раз; метрика flat = silent failure. Процессы: один consumer (PID==1); PID trace chain; PID старше правки → stop all → start one → verify log (12-15s → свежие строки → нет ERROR).
3. Зависание: маркер в начале блока; прогресс в файл; малый таймаут; A && B && C разделять; инфраструктура первой; git diff.
4. Многофакторный → ACH; застрял → форма (раздел 7) → лестница (раздел 8).
5. Фикс: один → stop-all-then-start-one → свежие строки лога (фильтр по времени старта!) → smoke дословно. Ошибки: сначала --help.

## Чеклист инцидента

- [ ] факты до гипотез; Capture до ретрая; симптом отделён, корень один раз
- [ ] маркеры прогресса; таймауты; один consumer; PID новый; лог по свежим строкам; кэш исключён; гонка монтирования исключена
- [ ] форма застревания + лестница; ≥2 гипотезы опровержениями (многофакторный); вывод: факт + root cause + один фикс + smoke

## 10. Постмортем после устранения (ресёрч 19.08: agent-axiom template, Yun1976/ai-agent-incidents — 33 урока реальных инцидентов)

1. **Сводка:** incident_id/дата/severity/owner/что произошло одной фразой.
2. **Цепочка:** агент/тул, вход (промпт/контекст/триггер), отказавшее действие, реальный ли побочный эффект.
3. **Артефакты:** session_id, trace (sessions.jsonl, trajectory_audit.py), approval_mode, конфиг. Не заполняется быстро = проблема observability.
4. **Локализация:** что отключили в первые минуты; сдерживание vs постоянная коррекция.
5. **Корень:** причина + усиливающие факторы + какой гейт провалился + слой (политика/права/память/observability).
6. **Правило в канон:** урок → канон/скилл/CHANGELOG (CYCLE.md). Индустрия: делегирование — закрытый цикл; голый `except` = тихий отказ; «не фейкуй» — неподтверждённая возможность = её нет.
