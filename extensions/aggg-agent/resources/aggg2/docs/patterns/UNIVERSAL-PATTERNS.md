# Универсальные паттерны (саморефлексия)

## ЗАЩИТА ОТ РЕГРЕССИЙ — универсальный паттерн (урок из инцидента: тема в voice-web)

Инцидент: правка «убрать хардкод темы» случайно удалила строку `root.dataset.theme = "light"` —
клик менял только подсветку кнопки, тема переключалась лишь после перезагрузки страницы. Верификация
«прошла», потому что прогонялась ДО этой правки, а путь восстановления при релоаде маскировал баг.

Универсальные правила — применимы к любой правке, не только к теме:

1. **Правка ≠ готово. Правка = новый черновик.** После каждой замены перечитай ВСЮ изменённую
   функцию/блок целиком, а не хвост диффа. Сверь баланс строк: было N, стало N + добавлено − удалено.
   Пропавшая строка — самый частый регресс.
2. **Верификация — ПОСЛЕ последней правки, и только она.** Тест/скриншот/прогон ДО правки не доказывает
   правку. Был хоть один правящий шаг между «проверил» и «готово» — проверка недействительна.
3. **Прогоняй сценарий пользователя дословно.** Сказал «клик не переключает» — кликни БЕЗ перезагрузки
   и проверь состояние синхронно. Пути восстановления (reload, restore, fallback) маскируют баги — они не тест.
4. **Аномалия = баг, пока не доказано обратное.** Неожиданное значение (атрибут не встал, цвет не тот) —
   это баг. Не списывай на «шум среды/кэш/кросс-таб» без проверки: синхронно, в одной вкладке,
   с чистым storage, curl'ом фактически отданных байт.
5. **Одно состояние — одно место.** Состояние (тема, режим, выбор) живёт в ОДНОМ источнике
   (атрибут/переменная/флаг). Инлайн-стили + атрибут + localStorage + класс — каждый дубль точка
   расхождения. Понадобились два места? Это смэлл — рефактори.
6. **Старый кэш выглядит как неисправленный баг.** Жалоба «всё ещё сломано» → сначала проверь,
   что сервер ОТДАЁТ исправленные байты (curl + grep строки-маркера правки), потом заставь кэш умереть:
   версия в URL (?v=N), no-cache на HTML.
7. **Минимальная правка + дифф интента.** Меняй ровно то, что заказано. После правки сравни
   «что должно было измениться» с «что изменилось». Лишняя строка в диффе — такая же ошибка, как пропавшая.

## УНИВЕРСАЛЬНЫЕ ПАТТЕРНЫ: ОКОННЫЙ РЕЖИМ И РЕДАКТИРОВАНИЕ (сессия voice-web desktop)

Уроки из оконной обёртки (pywebview/WebView2) и трёх само-регрессий при правках:

1. **Правка съедает соседнюю строку — трижды за сессию** (dataset.theme, .brand-mark,
   закрывающий `"""` docstring + дубль basicConfig). После ЛЮБОЙ SWAP-замены перечитай заново
   ВЕСЬ изменённый файл/функцию, а не место правки — пропадает не то, что трогал, а соседнее.
2. **GUI-обёртки: инициализация многослойная и асинхронная.** window.native → form.browser →
   CoreWebView2 появляются в разное время. Жди ВСЮ цепочку готовности, а не первый объект —
   гонка «первый есть, нужного ещё нет» даёт ложный AttributeError.
3. **pythonw (без консоли): stdout/stderr = None.** StreamHandler молча теряет логи.
   Процессы, которые могут стартовать без консоли, обязаны писать в ФАЙЛ (FileHandler),
   stdout — только дополнение.
4. **Хост-API по умолчанию DENY.** WebView2 без обработки PermissionRequested молча отклоняет
   микрофон. Фича с системным разрешением не работает без явного хука — проверяй, не предполагай
   «по умолчанию разрешено».
5. **Кто поднял ресурс — тот и гасит.** Сервер уже слушает порт → он чужой → не останавливать
   при закрытии окна. Владение ресурсом делай явным (проверка порта).
6. **Проверяй интеграцию живым запуском, но честно граничь.** Окно проверил: процесс жив,
   лог хука, запросы на сервер. Клик по кнопке записи в WebView2 не делал — так и сказано.
   Не выдавай «проверил запуск» за «проверил всё».

## ЗАЩИТА ОТ ЗАВИСАНИЙ — универсальный паттерн (урок из инцидента: завис Pester, 2026-08-03)

Инцидент: полный прогон тестов завис — два таймаута (900с и 300с) сожжены впустую, а агент
часами рассуждал статически: «этот тест мгновенный, не может зависнуть», перебирал тесты по
одному и дважды угадывал API Pester с неверными параметрами. Локализация заняла один запуск
с прогресс-выводом в файл: последний маркер «Describing …» указал блок, внутри которого зависло.

Правила — применимы к любому зависанию (тесты, скрипты, MCP, серверы, пайплайны):

1. **«Не может зависнуть» — не аргумент.** Зависнуть может что угодно: сеть без таймаута,
   Read-Host/ожидание ввода, dot-source с интерактивным промптом, бесконечный цикл, GUI-обвязка.
   Статический анализ не доказывает отсутствие зависания — доказывает только запуск с таймаутом.
2. **Локализуй маркером прогресса, а не последней строкой.** Маркер («Describing X»,
   «=== этап N ===») печатается в НАЧАЛЕ блока → зависло ВНУТРИ последнего блока, успевшего
   напечатать маркер. Нет маркеров — добавь их перед каждым этапом.
3. **Прогресс — в ФАЙЛ, не в пайп.** `cmd 2>&1 | Out-File prog.txt` — пайп в tail/Select может
   сам зависнуть или потерять хвост при убийстве по таймауту. Читай файл после.
4. **Изолируй подозреваемого ДО полного прогона.** Один тест/блок с МАЛЕНЬКИМ таймаутом
   (30–60с), а не весь набор с 900с. Полный прогон для локализации — трата времени.
5. **Сначала API инструмента, потом запуск.** `Get-Help` / `--help` — одна проверка экономит
   раунд. Две неудачные попытки с угаданными параметрами = минус два таймаута и ноль информации.
6. **Цепочка `A && B && C` маскирует место зависания.** Один зависший этап блокирует всё и
   выглядит как «зависла вся команда». Разделяй этапы: каждый — отдельная команда, свой таймаут,
   свой маркер.
7. **Первый подозреваемый — инфраструктура, не логика.** BeforeAll/dot-source/модули/сеть/
   интерактив виноваты чаще, чем тест, который «мгновенный». Сначала обвязка, потом тест.
8. **Сравни с последним успешным прогоном.** Что ИЗМЕНИЛОСЬ с тех пор (git diff, список файлов,
   новые модули)? Виновник обычно в изменениях, а не в старых строках.
9. **Таймаут — всегда и прогрессивный.** Сначала маленький на подозреваемое; увеличивай только
   если операция легитимно долгая. Таймаут — страховка, сужение — лечение.

## ДОЛГИЕ КОМАНДЫ ≠ БЛОКИРОВКА СЕССИИ (урок 2026-08-05: verify ~4.5 мин, eval-ядро 130, cancelled install)

Инцидент: `aggg verify` (MCP handshake всех серверов) идёт ~4.5 минуты. Прогон через eval с
capture_output и таймаутом 300с убил ядро (код 130) без результата; прогон через пайп python-декодера
упал на cp1251 (UnicodeDecodeError, байт 0xac); модуль установки инфраструктуры (qdrant+ollama)
отменился молча — «Command cancelled» без единой строки вывода. Три попытки, ноль информации — чистый блок.

Правила — применимы к ЛЮБОЙ долгой операции (verify, установщики, индексация, тесты, сборки):

1. **Долгая операция (>60с) — НЕ в eval с capture_output.** Это убивает ядро/вызов без результата.
   Только: bash с явным таймаутом + запись в файл, или async/фон (bash async / hub start). Запустил →
   продолжай другую работу → файл прочитаешь в конце. Паттерн индустрии: job id + лог-файл + sentinel
   завершения, агент — наблюдатель, не владелец процесса.
2. **Команда без вывода >30–60с = подозрение на зависание.** Маркеры в НАЧАЛЕ этапов («=== этап N ===»),
   прогресс в ФАЙЛ (Out-File), не в пайп. Детерминированный прогресс (X из Y) лучше спиннера.
3. **Разбивай большие операции на шаги** (install → qdrant → ollama → тест): каждый шаг — отдельная
   команда, свой таймаут, свой маркер. Один зависший этап не маскирует остальные и сразу локализуется.
4. **Sentinel-маркер завершения.** Пиши в файл «VERIFY DONE» / «RC=N» — проверяй по маркеру, не по
   таймауту. Sentinels переносимы и работают, даже когда менеджер процессов врёт.
5. **Кодировка вывода Windows: PowerShell/pwsh отдаёт cp1251** (байты 0xac и пр.). python
   decode('utf-8') падает. Декодируй cp1251 errors=replace, или пиши вывод в файл и читай через read.
6. **Число проверок — из вывода verify, не из grep скрипта.** `grep -c "Check "` дал 56, доки говорили 59,
   чей-то тест ждал 62 — три разные цифры. Правда — строка «VERIFY: PASS (N)» из самого вывода.
   Счётчик в verify динамический: `$total = $script:passes + $script:failures.Count`.
7. **Idle-таймаут (нет вывода N секунд) ловит зависание, wall-clock ловит затянутость.** Оба нужны:
   idle 60с на подозреваемое, wall-clock 600с на легитимно долгое.

## NPM CI НА ЖИВОМ MCP-РАНТАЙМЕ = EPERM (урок 2026-08-05)

Инцидент: переустановка рантайма rag-memory (npm ci) при живых серверах харнесса упала дважды подряд:
`EPERM unlink vec0.dll (-4048)` — нативный DLL залочен LoadLibrary'ом работающего node-процесса.
Хуже: первый npm ci успел снести JS-файлы (unlink разрешён) и оставил dist пустым — любой рестарт
сервера упал бы, хотя процессы продолжали работать из памяти.

Правила:
1. Переустановка node_modules под живым процессом, загрузившим эти файлы, падает на первом залоченном
   нативном файле (.dll/.node не удаляются, JS — да) → получается полумёртвое дерево.
2. Сначала останови MCP-серверы (это процессы агентов — родители перезапустят сами), потом npm ci.
3. DELETE_PENDING: файл может «числиться удалённым», пока хендл открыт — не пересоздавай поверх.
4. Паттерн подтверждён сообществом (npm issue tracker: блокирующий процесс может быть тем же node,
   который пытается удалить).
5. Холодный старт MCP с загрузкой модели эмбеддингов (onnxruntime) отвечает на initialize дольше 20с —
   таймаут handshake 60с; таймаут = ретрай, не диагноз «сломан».
