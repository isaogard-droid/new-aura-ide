# L. ПАТТЕРНЫ ПОВЕДЕНИЯ ИИ (извлечено из боевой сессии рефакторинга)

---

## L1. MAP BEFORE CUT
**Принцип:** Прежде чем трогать код, ИИ составляет карту: функции, классы, импорты, тесты.
**Правило:** Read + Grep по всем ключевым символам. Сначала понять границы, потом резать.
**Антипаттерн:** Начать выносить модули вслепую, получить циклические импорты.
**Признак:** Первые 5-10 действий — чтение и поиск, ни одного Edit.

---

## L2. SAFE LAYER FIRST
**Принцип:** ИИ выносит runtime/конфиг/утилиты (без зависимостей от Telegram) до handler'ов.
**Правило:** Сначала bot_runtime, bot_ui, bot_pipeline — чистые функции. Потом handlers с Telegram-зависимостями.
**Антипаттерн:** Выносить всё сразу в одном большом рефакторинге.
**Признак:** Создание модулей идёт от наименее зависимого к наиболее зависимому.

---

## L3. COMPATIBILITY FACADE PATTERN
**Принцип:** ИИ сохраняет старые публичные имена в bot.py, чтобы тесты и внешние импорты не сломались.
**Правило:** Старый bot.py остаётся точкой сборки с re-export'ами и адаптерами.
**Антипаттерн:** Переименовать всё сразу, тесты красные, фикс в 20 местах.
**Признак:** bot.py уменьшается, но все старые имена доступны через него же.

---

## L4. IMPORT-AND-LINT LOOP
**Принцип:** После каждого разреза ИИ проверяет импорт и ruff.
**Правило:** Edit -> Execute ruff/compileall -> fix -> repeat.
**Антипаттерн:** Написать 500 строк, потом запустить — 50 ошибок.
**Признак:** Цикл Edit-Execute длиной 2-3 итерации на каждый модуль.

---

## L5. ONE SYMBOL AT A TIME REMOVAL
**Принцип:** ИИ удаляет лишние импорты и функции по одному, проверяя после каждого.
**Правило:** Удалил импорт -> запустил ruff -> если ошибка — вернул.
**Антипаттерн:** Удалить 10 импортов за раз, не понять какой нужен.
**Признак:** Множество мелких Edit на 1-2 строки каждый.

---

## L6. TEST-PRESERVING REFACTOR
**Принцип:** ИИ запускает тесты после каждого крупного шага, чтобы убедиться что поведение не изменилось.
**Правило:** После выноса слоя -> pytest. Если тесты падают — чинить wiring, не функциональность.
**Антипаттерн:** Рефакторинг «на глазок», тесты зелёные случайно.
**Признак:** pytest запускается 3-5+ раз за сессию.

---

## L7. BIND NAMESPACE PATTERN
**Принцип:** ИИ передаёт handler-модулям общий namespace через bind(), чтобы избежать циклических импортов.
**Правило:** handlers/ получают globals() через bind(namespace) с _LOCAL_NAMES защитой.
**Антипаттерн:** Прямой import bot из handler-модуля -> циклическая зависимость.
**Признак:** В каждом handler-модуле есть функция bind(namespace) и _LOCAL_NAMES.

---

## L8. _LOCAL_NAMES GUARD
**Принцип:** ИИ сохраняет ссылки на локальные имена модуля до bind(), чтобы не перезаписать их чужими.
**Правило:** _LOCAL_NAMES = set(globals()) в начале модуля; bind() пишет только то, чего нет в _LOCAL_NAMES.
**Антипаттерн:** globals().update(namespace) без защиты — чужие имена затирают свои.
**Признак:** В каждом handler-модуле есть _LOCAL_NAMES и bind() с проверкой.

---

## L9. FACTS-FIRST, THEN THEORY
**Принцип:** ИИ идёт от storage/logs/process list к гипотезам, а не наоборот.
**Правило:** Сначала PID, log lines, DB row. Потом «наверное …».
**Антипаттерн:** «Наверное кэш» без проверки фактов.
**Признак:** Первые команды в дебаге — Get-CimInstance, Get-Content лога, проверка файлов.

---

## L10. PID TRACE CHAIN
**Принцип:** ИИ строит дерево процессов: родительский PID -> launcher -> рабочий каталог.
**Правило:** Get-CimInstance Win32_Process с фильтром по пути и ParentProcessId.
**Антипаттерн:** Смотреть только на PID, не понимать кто кого запустил.
**Признак:** В выводе всегда есть ParentProcessId и CommandLine.

---

## L11. LOG TIMELINE CORRELATION
**Принцип:** ИИ сопоставляет время в логе с временем редактирования/запуска.
**Правило:** Сравнить LastWriteTime файла с timestamp в логе. Если лог старше редактирования — процесс не перезапущен.
**Антипаттерн:** Видеть «Application started» в логе и думать что новый код работает.
**Признак:** В явном виде сравниваются modified time файла и log timestamp.

---

## L12. SYMPTOM vs ROOT CAUSE SEPARATION
**Принцип:** ИИ отличает видимую ошибку (NameError в cmd_balance) от истинной причины (неполный namespace wiring).
**Правило:** Трассировать call path до точки отказа, чинить корень, не симптом.
**Антипаттерн:** Патчить каждый handler, где падает, вместо фикса bind().
**Признак:** После фикса одной точки закрываются все поверхности ошибки.

---

## L13. SMOKE WITH ISOLATED LOCK
**Принцип:** ИИ запускает smoke-проверку с временным lock-файлом, чтобы не конфликтовать с production.
**Правило:** $env:BOT_LOCK_PATH = временный путь; старт и немедленный Stop-Process.
**Антипаттерн:** Запустить второй экземпляр на том же lock — Conflict в логе.
**Признак:** Каждый smoke использует уникальный lock-файл.

---

## L14. THREE-STEP VERIFICATION
**Принцип:** ИИ проверяет в порядке: ruff -> compileall -> pytest.
**Правило:** Никогда не пропускать шаги. Сначала линтер, потом компиляция, потом тесты.
**Антипаттерн:** Сразу запустить тесты — они падают из-за синтаксиса, теряется время.
**Признак:** Три Execute подряд: ruff check, compileall, pytest.

---

## L15. DEFINITION OF DONE (4-STEP)
**Принцип:** ИИ считает задачу выполненной после: parse, import, test, one live process.
**Правило:** ast/syntax -> import module -> pytest -> single instance up -> log ok.
**Антипаттерн:** «Закоммитил» = «готово» без проверки runtime.
**Признак:** Финальный ответ содержит 4 пункта проверки.

---

## L16. CROSS-MODULE REFERENCE INSPECTION
**Принцип:** ИИ проверяет что два модуля ссылаются на один объект, а не на копию.
**Правило:** print('same pending', bot._pending is media._pending) — проверка identity.
**Антипаттерн:** Предполагать что импорт даёт тот же объект без проверки.
**Признак:** В коде проверки есть is-сравнение объектов между модулями.

---

## L17. STOP-ALL-THEN-START-ONE
**Принцип:** ИИ убивает все старые процессы перед запуском нового.
**Правило:** Stop-Process старых PID -> Start-Process нового -> verify log.
**Антипаттерн:** Запустить поверх — два процесса с одним токеном, Conflict.
**Признак:** Перед стартом всегда есть Stop-Process по id.

---

## L18. TOKEN ISOLATION BY LAUNCHER
**Принцип:** ИИ чистит переменные окружения в каждом launcher, чтобы токены не протекали.
**Правило:** Каждый .cmd файл удаляет чужой TELEGRAM_BOT_TOKEN перед запуском.
**Антипаттерн:** Один secrets.env для всех ботов.
**Признак:** В run_prod.cmd есть $env:TELEGRAM_BOT_TOKEN='', в run_cbt.cmd тоже.

---

## L19. LOCAL TOKEN OVERRIDE
**Принцип:** ИИ даёт приоритет local.token над env-переменной для изоляции.
**Правило:** Если local.token существует — читать его, иначе env.
**Антипаттерн:** Только env — при тестировании можно случайно запустить prod.
**Признак:** В bot_runtime.py: if local_token.is_file(): return local_token.read_text().

---

## L20. SINGLE CONSUMER GUARD
**Принцип:** lock-файл не даёт запустить второй экземпляр того же бота.
**Правило:** acquire_instance_lock() проверяет file lock при старте.
**Антипаттерн:** Нет lock — два процесса, оба получают половину updates.
**Признак:** В runtime есть acquire_instance_lock() с file lock.

---

## L21. LAUNCHER PATH IS ANCHOR
**Принцип:** ИИ использует путь launcher'а чтобы отличить один бот от другого.
**Правило:** Фильтр процессов по CommandLine contains пути проекта.
**Антипаттерн:** Фильтровать только по имени python.exe — найти все процессы.
**Признак:** Get-CimInstance Where-Object CommandLine -match 'tg-voice-bot'.

---

## L22. PROCESS CREATION TIME CHECK
**Принцип:** ИИ сверяет время создания процесса с временем редактирования кода.
**Правило:** Если CreationDate < edit time — процесс старый, не на новом коде.
**Антипаттерн:** Думать что процесс сам обновился после редактирования файла.
**Признак:** Сравнение CreationDate процесса с LastWriteTime файла.

---

## L23. GREP FIRST, READ SECOND
**Принцип:** ИИ сначала ищет паттерны через Grep, потом читает конкретные файлы.
**Правило:** Grep «^(async )?def » -> Read bot.py (только нужные строки).
**Антипаттерн:** Читать весь файл из 2500 строк, чтобы найти 5 функций.
**Признак:** Перед Read всегда один или несколько Grep.

---

## L24. AST ANALYSIS BEFORE SURGERY
**Принцип:** ИИ анализирует AST файла, чтобы понять структуру до редактирования.
**Правило:** ast.parse + итерация по FunctionDef/ClassDef — карта модуля.
**Антипаттерн:** Редактировать вслепую, не зная где заканчивается функция.
**Признак:** Execute с inline Python-скриптом ast.parse перед Edit.

---

## L25. TWO-PHASE IMPORT CLEANUP
**Принцип:** ИИ сначала удаляет очевидно лишние импорты, потом прогоняет ruff — повторяет.
**Правило:** Убрал atexit/html/wave -> ruff -> F401 остаток -> убрал остальное -> ruff.
**Антипаттерн:** Удалить всё сразу — потерять нужный импорт.
**Признак:** 2-3 цикла Edit-Execute по импортам.

---

## L26. ALIAS RENAMING FOR SAFE ADAPTER
**Принцип:** ИИ даёт вынесенным функциям псевдонимы (as _edit_html, as _fmt_result), сохраняя старые имена.
**Правило:** from bot_ui import edit_html as _edit_html, fmt_result as _fmt_result.
**Антипаттерн:** Прямой import — конфликт имён между модулями.
**Признак:** В импортах есть as _имя для вынесенных функций.

---

## L27. hasattr SAFETY GUARD
**Принцип:** ИИ оборачивает доступ к ctx.user_data в hasattr, потому что тестовый FakeCtx его не имеет.
**Правило:** if hasattr(ctx, «user_data»): ctx.user_data[…] = …
**Антипаттерн:** Прямой ctx.user_data — AttributeError в тестах.
**Признак:** Все обращения к user_data обёрнуты в hasattr или getattr.

---

## L28. MODULE-LEVEL STATE ALIAS
**Принцип:** ИИ синхронизирует state между модулями через прямую ссылку, а не через копию.
**Правило:** media._pending = _pending (один объект, два имени).
**Антипаттерн:** media._pending = dict(_pending) — копия, state расходится.
**Признак:** В коде есть присваивание module.attr = module.attr (ссылка на тот же объект).

---

## L29–L50 — вынесено в `glav/l-ai-behavior-2.md` (резка god-файла, docs/canon/FILE-SIZE.md)

**Правило:** namespace.update({«cmd_history»: history.cmd_history, …}) — явный словарь.
**Антипаттерн:** globals().update(namespace) — случайные имена перезаписывают друг друга.
**Признак:** В bot.py есть явный словарь маппинга имён из модулей.
