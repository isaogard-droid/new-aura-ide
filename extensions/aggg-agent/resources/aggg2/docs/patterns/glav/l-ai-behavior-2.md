# L. ПАТТЕРНЫ ПОВЕДЕНИЯ ИИ (часть 2: L29–L50)

Вынесено из `l-ai-behavior.md` (механическая резка god-файла:
soft-лимит доков 300 строк, docs/canon/FILE-SIZE.md). Полная карта — `GLAV-PATTERNS.md`.

---

## L29. PARALLEL TOOL CALLS
**Принцип:** ИИ делает несколько Read/Grep/Execute в одном ответе, чтобы ускорить сбор информации.
**Правило:** Read 3 files + Grep 2 searches в одном сообщении.
**Антипаттерн:** Читать файлы по одному, тратить 5 раундов на сбор данных.
**Признак:** В одном ответе 2-5 параллельных вызовов инструментов.

---

## L30. PLAN AS WORKING MEMORY
**Принцип:** ИИ использует Plan updated как чекпоинт и коммуникацию с пользователем.
**Правило:** После каждого шага — короткий Plan updated со статусом.
**Антипаттерн:** Молча делать шаги, пользователь не понимает прогресс.
**Признак:** Каждый 2-3 ответ содержит Plan updated.

---

## L31. SKILL ACTIVATION AT TASK START
**Принцип:** ИИ активирует skill (ponytail, debugging) в начале задачи, не по ходу.
**Правило:** Skill ponytail -> Skill debugging-and-error-recovery в первых сообщениях.
**Антипаттерн:** Начать без навыка, переключиться посередине.
**Признак:** Skill activated в начале сессии, до первого Edit.

---

## L32. EXECUTE WITH INLINE PYTHON
**Принцип:** ИИ использует Execute с inline Python-скриптом (-c) для анализа, когда shell недостаточно.
**Правило:** $script = @' … import ast … '@; & python -c $script.
**Антипаттерн:** Пытаться сделать AST-анализ через PowerShell — мучительно.
**Признак:** Execute с многострочным Python-скриптом через -c.

---

## L33. Start-Sleep BEFORE LOG CHECK
**Принцип:** ИИ ждёт 10-15 секунд после запуска процесса, прежде чем читать лог.
**Правило:** Start-Sleep -Seconds 12; Get-Content лога.
**Антипаттерн:** Читать лог сразу после старта — пусто или неполно.
**Признак:** Перед Get-Content лога всегда есть Start-Sleep.

---

## L34. FIRE-AND-FORGET WITH PID CAPTURE
**Принцип:** ИИ запускает процесс в фоне, сохраняет PID, потом проверяет жив ли.
**Правило:** $proc = Start-Process … -PassThru; $proc.Id; потом Get-Process -Id.
**Антипаттерн:** Запустить и забыть — не знать жив ли процесс.
**Признак:** После Start-Process сразу проверка running_before_stop.

---

## L35. STATUS BULLET SUMMARY
**Принцип:** ИИ выдаёт статус маркированным списком без лишних слов.
**Правило:** • bot A: PID X, running • bot B: PID Y, stopped.
**Антипаттерн:** Эссе на 20 строк с описанием каждого шага.
**Признак:** Ответ начинается с маркированного списка из 2-4 пунктов.

---

## L36. RUSSIAN-ENGLISH CODE SWITCHING
**Принцип:** ИИ говорит с пользователем по-русски, но код и команды — на английском.
**Правило:** Сообщение на русском, код/команды/логи на английском.
**Антипаттерн:** Переводить сообщения об ошибках на русский.
**Признак:** Русский текст в ответе, английский в коде и логах.

---

## L37. ACTIONABLE NEXT STEP
**Принцип:** ИИ завершает ответ конкретным действием для пользователя.
**Правило:** «Запускай через run_prod.cmd» или «Проверь лог по пути X».
**Антипаттерн:** «Вроде ок» без указания что делать дальше.
**Признак:** Последняя строка ответа — команда или инструкция.

---

## L38. EMOTIONAL CALIBRATION
**Принцип:** ИИ подстраивает тон под пользователя: мат пользователя -> более неформальный ответ.
**Правило:** «заебись» пользователя -> «будет заебись» в ответе.
**Антипаттерн:** Официальный тон на неформальный запрос.
**Признак:** Словарь ответа повторяет словарь пользователя.

---

## L39. GRADUAL ERROR NARROWING
**Принцип:** ИИ сужает круг поиска от общего к частному: все процессы -> PID -> CommandLine -> лог -> строка.
**Правило:** Get-CimInstance -> Where-Object по пути -> Get-Content -> Select-String.
**Антипаттерн:** Сразу читать конкретный файл лога, не проверив какой процесс его пишет.
**Признак:** Цепочка из 3-4 команд с фильтрацией на каждом шаге.

---

## L40. COMMAND FAILURE RETRY WITH SIMPLIFICATION
**Принцип:** Если команда падает с синтаксической ошибкой, ИИ упрощает её и пробует снова.
**Правило:** Убрать пайплайн, разбить на шаги, использовать более простой синтаксис.
**Антипаттерн:** Повторять ту же сложную команду 5 раз.
**Признак:** После ошибки синтаксиса — упрощённая версия команды.

---

## L41. THREE-STATE ERROR CLASSIFICATION
**Принцип:** ИИ классифицирует ошибки: import (F401/F821), syntax (ParserError), runtime (NameError/Conflict).
**Правило:** Сначала fix import, потом syntax, потом runtime. Каждый класс отдельно.
**Антипаттерн:** Чинить NameError, когда есть F401 — имя всё равно не импортится.
**Признак:** После ruff -> compileall -> pytest, именно в этом порядке.

---

## L42. ERROR RECOVERY BY ROLLBACK
**Принцип:** Если фикс не помог, ИИ откатывает изменение и пробует другой подход.
**Правило:** Edit -> fail -> Edit (вернуть как было) -> другой Edit.
**Антипаттерн:** Углублять неправильный фикс, делая хуже.
**Признак:** В истории есть пары Edit-Edit (туда-обратно).

---

## L43. VALUE SLICE ORDER
**Принцип:** ИИ делает сначала core, потом money, потом UX, потом growth.
**Правило:** pipeline -> billing -> history -> admin -> referrals.
**Антипаттерн:** Делать админку до того как работает биллинг.
**Признак:** Порядок модулей в рефакторинге: runtime, ui, pipeline, handlers.

---

## L44. LAZY ARCHITECTURE (YAGNI)
**Принцип:** ИИ не создаёт абстракции, пока нет второго потребителя.
**Правило:** Inline код, пока не появится второй модуль с тем же функционалом.
**Антипаттерн:** AbstractRepository с одной имплементацией «на вырост».
**Признак:** В рефакторинге нет интерфейсов, абстрактных классов, базовых классов.

---

## L45. SHARED ROOT OVER COPY-PASTE
**Принцип:** ИИ выносит дублированный код в одно место, а не копирует фикс.
**Правило:** Одна guard в shared функции > 10 патчей в callers.
**Антипаттерн:** Починить voice, но audio всё ещё free.
**Признак:** Вынесенная функция используется из 2+ мест.

---

## L46. MEASUREMENT OVER ARGUMENT
**Принцип:** ИИ предпочитает показать цифру (лог/метрику), чем спорить.
**Правило:** «Лог charged secs=61» вместо «мне кажется списывается правильно».
**Антипаттерн:** Час теории без одной строки evidence.
**Признак:** В ответе есть цитата из лога или результат проверки.

---

## L47. SELF-CORRECTING LOOP
**Принцип:** ИИ проверяет свои действия и исправляет ошибки без внешней команды.
**Правило:** Edit -> Execute -> error -> fix -> Execute -> ok. Без вопроса пользователю.
**Антипаттерн:** Спрашивать «что делать?» при каждой ошибке.
**Признак:** Цепочка действий без ответа пользователю между ними.

---

## L48. COMPACTION AWARENESS
**Принцип:** ИИ учитывает, что история сообщений может быть сжата (compact).
**Правило:** После compaction — повторный Read файлов, которые могли быть в сжатой истории.
**Антипаттерн:** Продолжать с того же места, файлы уже не в контексте.
**Признак:** После «Your message history was compacted» — повторный Read/Grep.

---

## L49. CONTEXT PRESERVATION ACROSS COMPACTION
**Принцип:** ИИ повторяет ключевые факты после compaction, чтобы не потерять нить.
**Правило:** «Plan updated» с текущим статусом после compaction.
**Антипаттерн:** Продолжить как ни в чём не бывало — потеря контекста.
**Признак:** После compaction — полный Plan updated со всеми пунктами.

---

## L50. TOKEN BUDGET MANAGEMENT
**Принцип:** ИИ читает файлы с offset/limit, чтобы не исчерпать лимит токенов на огромный файл.
**Правило:** Read -Offset 200 -Limit 400 для файла из 2000 строк.
**Антипаттерн:** Читать весь 2000-строчный файл за раз.
**Признак:** Read с параметрами offset и limit для больших файлов.

---

## L51. RECURSIVE SELF-DEBUG
**Принцип:** ИИ включает навык debugging-and-error-recovery когда заходит в тупик.
**Правило:** Skill debugging-and-error-recovery -> повторный анализ -> новая стратегия.
**Антипаттерн:** Продолжать ошибочную стратегию.
**Признак:** Skill activated debugging-and-error-recovery в середине сессии.

---

## L52. COMPATIBILITY OVER PURITY
**Принцип:** ИИ жертвует архитектурной чистотой ради совместимости с существующими тестами.
**Правило:** Оставить facade-функции даже если они просто делегируют, потому что тесты их monkeypatch'ят.
**Антипаттерн:** Идеальная архитектура, все тесты красные.
**Признак:** Есть facade-функции, которые только вызывают _функцию из модуля.

---

## L53. TWO-WAY MERGE STRATEGY
**Принцип:** ИИ переносит архитектурные модули в production, но не трогает production-специфичные файлы.
**Правило:** Copy bot_runtime/bot_ui/bot_pipeline/handlers, но не трогать access.py/voice.py/generators.py.
**Антипаттерн:** Полная замена production на CBT — сломать production-специфику.
**Признак:** Copy-Item с выборочным списком файлов, diff production vs CBT.

---

## L54. EXPLICIT CROSS-MODULE WIRING
**Принцип:** ИИ явно прописывает связи между модулями, а не надеется на совпадение имён.
**Правило:** namespace.update({«cmd_history»: history.cmd_history, …}) — явный словарь.
**Антипаттерн:** globals().update(namespace) — случайные имена перезаписывают друг друга.
**Признак:** В bot.py есть явный словарь маппинга имён из модулей.
