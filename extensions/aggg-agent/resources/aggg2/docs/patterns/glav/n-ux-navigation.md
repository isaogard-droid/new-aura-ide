# N. УНИВЕРСАЛЬНЫЕ ПРИНЦИПЫ UX-НАВИГАЦИИ, КОНТЕКСТА И ИНТЕРАКЦИИ

---

## N1. VIEW STATE SEPARATION
**Принцип:** Текущий (fresh) результат и сохранённая (history) запись — разные состояния системы. Нельзя использовать один обратный маршрут для обоих.
**Правило:** Для fresh-результата — отдельный путь возврата (напр. «‹ К результату»). Для истории — свой (напр. «‹ К списку»).
**Антипаттерн:** Свежий результат использует history-маршрут для возврата — пользователь внезапно оказывается в списке старых записей.
**Признак:** Два разных обратных маршрута для fresh-view и history-view.

---

## N2. CONTEXT FLAG PROPAGATION
**Принцип:** Контекст (fresh/stale, edit/read, preview/export) передаётся булевым/перечислимым флагом через все слои: UI → actions → generators → callbacks.
**Правило:** `isFresh: bool = false` в сигнатурах; передаётся в каждый дочерний вызов. Ни один слой не теряет контекст.
**Антипаттерн:** Передать page=0 из свежего контекста — дочерняя операция возвращает в историю.
**Признак:** Флаг контекста (или его эквивалент) присутствует в сигнатурах всех функций, участвующих в цепочке.

---

## N3. ROUTE NAMESPACE BY SCENARIO
**Принцип:** Разные UX-сценарии получают разные префиксы/имена маршрутов: одно для возврата из просмотра, другое для возврата из генерации, третье для возврата из экспорта.
**Правило:** Каждый сценарий — свой префикс (back-to-result, back-from-edit, back-to-list). Маршруты не пересекаются.
**Антипаттерн:** Единственный «назад» для всех контекстов — невозможно понять откуда пришёл пользователь.
**Признак:** В роутере зарегистрированы отдельные правила для каждого сценария возврата.

---

## N4. EXPLICIT SOURCE LABELS
**Принцип:** Пользователь должен видеть, создан ли контент автоматически (системой) или вручную (по его запросу).
**Правило:** Разные иконки/префиксы для auto-generated и manually-requested контента. Никогда не смешивать.
**Антипаттерн:** И там и там одинаковый ярлык — пользователь не отличает автоматическое от ручного.
**Признак:** В UI используются разные префиксы/иконки для auto и manual контента.

---

## N5. MODEL OUTPUT HEADER STRIP
**Принцип:** Если модель/генератор возвращает заголовок, который UI уже показывает, — дубликат надо удалить перед отображением.
**Правило:** Функция очистки вырезает первую строку, если она совпадает с известным шаблоном заголовка.
**Антипаттерн:** Показать заголовок от модели поверх заголовка от UI.
**Признак:** Есть функция очистки вывода перед вставкой в UI.

---

## N6. CONTEXT-DEPENDENT LABEL FOR SAME ACTION
**Принцип:** Одно и то же действие может иметь разные подписи в зависимости от контекста, в котором оно показывается.
**Правило:** Параметр label/title в функции, формирующей UI. Caller задаёт label по контексту.
**Антипаттерн:** Хардкод одной подписи на все случаи.
**Признак:** В вызовах UI-функции передаётся параметр label или title.

---

## N7. NAVIGATION TARGET COMPUTED ONCE
**Принцип:** Цель возврата (куда вернётся пользователь) вычисляется один раз и используется во всех местах: и в тексте ссылки, и в callback-данных, и в кнопке.
**Правило:** `backTarget = isFresh ? "fresh" : historyPage` — одна переменная, N использований.
**Антипаттерн:** Дублировать строку маршрута в 5 местах — поменяли в 4, забыли в 5-м.
**Признак:** Переменная backTarget/backLink используется и в тексте, и в ссылке.

---

## N8. NON-DESTRUCTIVE NAVIGATION FIX
**Принцип:** Исправление навигации делается добавлением новых маршрутов, а не изменением схемы данных.
**Правило:** Добавить новый маршрут + handler; существующие не трогать. Схема БД/моделей не меняется.
**Антипаттерн:** Добавить поле isFresh/isNew в БД ради исправления навигации.
**Признак:** Diff содержит только handler'ы и роутер; схема данных не меняется.

---

## N9. INLINE AUTO vs LAYERED ON-DEMAND
**Принцип:** Автоматически сгенерированный контент показывается inline в основном результате; запрошенный вручную — отдельным слоем/экраном.
**Правило:** Auto → встроен в основной ответ; on-demand → отдельный вызов/переход.
**Антипаттерн:** Авто-контент отдельным слоем — два визуальных элемента там, где нужен один.
**Признак:** При auto-режиме результат содержит контент inline; при on-demand контент показывается по действию пользователя.

---

## N10. IMMEDIATE FEEDBACK + CONTENT UPDATE
**Принцип:** После любого действия пользователя: сначала краткий фидбек (что произошло), потом обновление контента.
**Правило:** Фиксированный протокол: 1) подтверждение действия (toast/alert); 2) обновление содержимого.
**Антипаттерн:** Только обновление контента без фидбека — пользователь не понимает что произошло.
**Признак:** Перед каждым обновлением контента есть фидбек с осмысленным текстом.

---

## N11. ENTRY EXISTENCE GUARD
**Принцип:** Перед рендерингом любой записи (из БД, кэша, API) — проверить что она существует.
**Правило:** `entry = getEntry(id); if not entry: return error("Не найдено")`.
**Антипаттерн:** `entry.field` без проверки — KeyError/AttributeError при удалённой записи.
**Признак:** Каждый доступ к getEntry обёрнут в проверку существования.

---

## N12. ROUTE REGISTRATION IN TWO PLACES
**Принцип:** Новый маршрут регистрируется в двух местах: в роутере (regex/pattern → handler) и в карте handler'ов (идентификатор → модуль.функция).
**Правило:** Добавил handler → добавил в роутер И в карту handler'ов.
**Антипаттерн:** Зарегистрировал только в одном месте — маршрут не работает.
**Признак:** Grep имени handler'а находит два вхождения: в роутере и в карте handler'ов.

---

## N13. CONTEXT PRESERVATION IN DEEP ACTIONS
**Принцип:** Кнопки дочерних действий (генерация, экспорт, трансформация) несут контекст родительского представления, чтобы вернуться правильно.
**Правило:** В параметрах действия передаётся идентификатор контекста (fresh/history, page number).
**Антипаттерн:** Дочернее действие передаёт page=0 всегда — после выполнения возвращает в начало, а не туда, откуда пришёл.
**Признак:** В callback-данных дочерних действий есть флаг/параметр контекста.

---

## N14. BEHAVIORAL TOGGLE DESCRIPTIONS
**Принцип:** Описание режима в настройках должно объяснять, что пользователь ПОЛУЧИТ в результате, а не только «вкл/выкл».
**Правило:** ВКЛ: «Система автоматически добавляет X к результату»; ВЫКЛ: «X показывается только по вашему запросу».
**Антипаттерн:** «Режим X: ВКЛ» без объяснения последствий.
**Признак:** Текст toggle-сообщения содержит сценарий использования, не только статус.

---

## N15. PAGINATED OUTPUT PRESERVES CONTEXT
**Принцип:** При разбивке длинного результата на части (чарки, страницы) каждый фрагмент сохраняет кнопку возврата в исходный контекст.
**Правило:** В цикле по фрагментам: каждый фрагмент содержит ссылку назад с контекстом.
**Антипаттерн:** Кнопка возврата только на первом или только на последнем фрагменте.
**Признак:** Каждый вызов отображения фрагмента содержит reply_markup/action с back-контекстом.

---

## N16. CACHE CHECK BEFORE EXPENSIVE OPERATION
**Принцип:** Перед вызовом дорогой операции (LLM, генерация, API) — проверить что результат уже не существует.
**Правило:** `cached = exists(kind); if cached: use existing; else: generate`.
**Антипаттерн:** Вызывать LLM на каждый клик кнопки — деньги и время улетают.
**Признак:** В обработчике действия есть проверка кэша до вызова дорогой операции.

---

## N17. VISIBLE TRUNCATION MARKER
**Принцип:** При обрезании длинного текста/контента добавлять видимый маркер, что показано не всё.
**Правило:** `text[:limit - marker.length] + marker` — маркер «…показано не всё».
**Антипаттерн:** Молча обрезать — пользователь не знает, что контент неполный.
**Признак:** Везде, где есть слайс по лимиту, есть маркер обрезания.

---

## N18. FIRST-VIEW vs REVISIT-VIEW DISTINCTION
**Принцип:** Один и тот же объект может выглядеть по-разному при первом показе и при повторном открытии из истории.
**Правило:** Первый показ: полные кнопки действий, акцент на контенте. Повторный: компактный вид, кнопки навигации по списку.
**Антипаттерн:** Одинаковые кнопки везде — непонятно, в каком режиме пользователь.
**Признак:** UI-функция принимает параметр isFirstView/isFresh и меняет набор кнопок.

---

## N19. MUTATE IN PLACE vs CREATE NEW
**Принцип:** Если контент уже показан — редактировать существующий элемент; если это новый контент — создавать новый.
**Правило:** Просмотр/детализация → edit_message/mutate in place. Новая генерация/экспорт → reply/create new.
**Антипаттерн:** Всегда создавать новый элемент — плодить дубликаты.
**Признак:** Действия просмотра используют mutate-in-place; действия создания — create-new.

---

## N20. STAGING-FIRST DEPLOYMENT
**Принцип:** Все изменения сначала валидируются в staging/test-окружении, потом синхронизируются в production.
**Правило:** Staging → тесты зелёные → diff → выборочный перенос в production → production-тесты.
**Антипаттерн:** Править сразу в production без проверки на staging.
**Признак:** Перед любым изменением production есть зелёный прогон в staging.

---

## N21. FULL FLEET RESTART AFTER CHANGE
**Принцип:** После любого изменения кода перезапускаются все экземпляры приложения, а не только один.
**Правило:** Остановить все → запустить заново → верификация логов каждого.
**Антипаттерн:** Перезапустить только один экземпляр — остальные на старом коде, поведение расходится.
**Признак:** После патча N запусков + N проверок логов.

---

## N22. NAVIGATION REGRESSION TEST
**Принцип:** Тест проверяет, что fresh-back возвращает на результат, а не в список/историю.
**Правило:** Создать тестовый объект → вызвать fresh-back → assert что в ответе контент объекта, а не список.
**Антипаттерн:** Исправить навигацию без теста — через неделю сломается рефакторингом.
**Признак:** Для каждого нового навигационного маршрута есть тест, проверяющий конечный контент.

---

## N23. PARAMETERIZED UI TESTS
**Принцип:** Если UI-функция меняет поведение/подписи от параметра — тест проверяет все варианты.
**Правило:** Для каждого параметра label/type/variant — тест с конкретным значением.
**Антипаттерн:** Параметризованная функция без теста на разные вызовы.
**Признак:** Для параметра, влияющего на UI, есть тест с каждым значимым значением.

## N43. POST-REFINEMENT LABEL AUDIT
**Принцип:** После реализации — пройтись по всем новым лейблам и убрать декоративные элементы (эмодзи, лишние знаки), которые попали в кнопки на этапе прототипирования.
**Правило:** Перед финальным деплоем: grep по label'ам кнопок → удалить эмодзи → обновить тесты → перезапустить.
**Антипаттерн:** Оставить декоративные эмодзи в кнопках потому что «уже работает».
**Признак:** Финальный diff содержит удаление эмодзи из button-лейблов и обновление assert в тестах.
