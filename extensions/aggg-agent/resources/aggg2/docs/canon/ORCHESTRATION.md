# Оркестрация: субагенты и multiorch.py

Два уровня раздачи работы агентам (проверены живьём): 1) субагенты харнесса (ноль
кода); 2) скрипт `scripts/tools/judge/multiorch.py`.

## Когда оркестрация нужна (а когда нет)

| Нужна | НЕ нужна |
|---|---|
| независимые куски (3+ направлений) | тривиальная правка — обычный цикл (CYCLE) |
| направления сильно разные (код/доки/конфиги) | одна связная задача в главном агенте |
| нужно «свежими глазами» | срочный фикс — быстрее руками |
| цена ошибки выше стоимости прогона | «мутная» цель без плана |

## Раздел 1. Оркестрация субагентами (путь A, без кода)

### Кто и чем запускает субагентов (явно)

- **Оркестратор = главный агент** (primary); fable-loop — СКИЛЛ, не исполнитель;
  инструкции — `fable-loop` (PLAN/EXECUTE/VERIFY/AUDIT) + `fable-method`.
- **Механизм запуска** — инструмент субагентов ХАРНЕССА: opencode — task tool
  (child-сессии, изоляция permissions), claude — Task tool, codex — subagents,
  reasonix — runAs: subagent.
- **Субагенты** — встроенные (explore/general/scout) или свои (`agent/<имя>/agents/*.md`,
  разноска `install_agents.py --subagents`).

Пользователь → **главный агент (оркестратор)** → task tool → N субагентов (отдельные
сессии, не видят друг друга) → синтез главным агентом.

### Механика (по fable-loop)
1. **PLAN**: 3-5 подзадач, каждой — инструкция воркеру + done-критерий задачи.
2. **EXECUTE (fan-out)**: субагенты ПАРАЛЛЕЛЬНО, одним сообщением; отдельные сессии.
   Read-only: «только читай и анализируй, НЕ редактируй».
3. **SYNTHESIS**: итог первым, противоречия воркеров — явно, пробелы — отдельно.
4. **VERIFY**: дорогие результаты — атакующий субагент («докажи, что вывод неверен»)
   или судья `multimodel_judge.py`.

**Когда A:** демо, быстро, нет задачи под скрипт; воркеры наследуют модель родителя
(мультимодельности нет).

**Грабли A:** permissions свои (read-only воркер может не видеть файлы вне workspace);
воркеры возвращают «сырьё» — синтез структурирует сам; сбой воркера не роняет панель:
«ОШИБКА» — в протокол.

## Раздел 2. Скрипт-оркестратор scripts/tools/judge/multiorch.py (путь B)

Планер сам разбивает задачу, воркеры — параллельно на указанной модели/бэкенде,
синтезатор собирает итог. Бэкенды — из `multimodel_judge` (opencode/reasonix/
codewhale/omp/claude/codex).

```bash
python3 scripts/tools/judge/multiorch.py --task "задача" --out /tmp/orch.md
python3 scripts/tools/judge/multiorch.py --task "..." --worker-model opencode/mimo-v2.5-free --cap 4
```

**Фазы:**
1. **PLAN** — планер (`--planner`, дефолт deepseek/deepseek-v4-pro) выдаёт JSON-план
   `{"tasks": [{"id", "title", "task"}]}`. Hard cap `--cap` (дефолт 5, макс 10) — против
   cost spikes (failure-режим: планер создал 20 воркеров, хватило 3).
2. **EXECUTE** — воркеры параллельно (ThreadPoolExecutor, изолированные сессии,
   `--worker-model`, дефолт opencode/mimo-v2.5-free), read-only по промпту; сбой одного
   не роняет панель.
3. **SYNTHESIS** — синтезатор (та же модель): главный вывод первым, результаты по
   подзадачам, противоречия, пробелы.

**Флаги:** `--task` (обязателен), `--planner`, `--worker-model`, `--cap`, `--harness`,
`--out` (протокол md), `--timeout`.

**Когда B:** повторяемый процесс, воркеры на другой модели/бэкенде, жёсткая схема
плана, протокол в файл. Воркеры — одна модель; per-task — будущая опция.

## A или B — выбор

| Критерий | Путь A (субагенты) | Путь B (multiorch.py) |
|---|---|---|
| Код | ноль | скрипт |
| Повторяемость | руками каждый раз | команда = одинаковый процесс |
| Модель воркеров | одна (родителя) | одна (`--worker-model`), бэкенд любой |
| Протокол | в чате | md-файл (`--out`) |
| Скорость старта | сразу | ~1 мин на аргументы |

## Грабли (проверено живьём)

- **JSON-парсинг:** модели вставляют JSON-примеры с фигурными скобками — срез по
  `rfind("}")` режет JSON; нужен балансный парсер (`extract_json_object` из multimodel_judge).
- **Hard cap обязателен:** без `--cap` планер раздувает план — стоимость умножается.
- **Стоимость:** паттерн — самый дорогой из мульти-агентных (планер + N воркеров +
  синтез); воркеры — дешёвые модели.
- **Воркеры read-only** — задача с правками это НЕ multiorch: правки — в главном агенте.
- **Ошибки харнессов:** код игнорирует returncode — ошибка внешнего вызова может
  выглядеть как «ответ модели» (аудит id=393; фикс в бэклоге).
