# changelog-discipline — журнал решений

Скилл для ведения CHANGELOG как **журнала решений**, а не истории версий. Полный текст и справки: `skills/changelog-discipline/SKILL.md`.

## Зачем нужен (какую боль закрывает)
Историю версий ведёт git. В коде НЕ найти: **почему выбрали этот путь, что было до, что отвергли**. Через полгода контекст забыт, и «исправить» решение обратно — вопрос времени.

## Когда использовать
| Использовать | НЕ использовать |
|---|---|
| после КАЖДОЙ правки кода в проекте с changelog | commit message |
| первое заведение changelog в новом проекте | описания PR |
| подготовка релиза | релиз-ноты для пользователей |
| «почему сделано так» без ответа в коде | — |
| «запиши, что решили/почему/что отвергли» | — |
В AGGG2.0 журналом решений служит research.db (внутренний); changelog — для проектов-продуктов, которые отдаются наружу.

## Опорные принципы
- **Адресат — «я через полгода»**: запись самодостаточна.
- **«Зачем» важнее «что»** — «что» покажет дифф, «зачем» — никто.
- **Отвергнутый вариант — золото**: защищает от «улучшения» обратно.
- **Писать сразу после правки** — отложенная запись вырождается в пересказ.
- **Без исключений** — одно пропущенное «мелочное» изменение делает журнал выборочным, а выборочному нельзя верить.

## Формат (сердце записи)
Резюме релиза — четыре поля:
| Поле | Смысл |
|---|---|
| **Что** | что теперь работает иначе — на языке продукта, не кода |
| **Где** | затронутые файлы и области |
| **Почему** | какую боль снимает, ради чего делалось |
| **Было** | как было раньше — единственное место, где прежнее поведение зафиксировано |
«Было» пропускают чаще всего — и зря.
Запись внутри секции: одна запись = одно решение (не один коммит): жирный заголовок-суть, что поменялось, почему выбрано так, что отвергнуто и почему.

## Порядок действий
1. Сразу после правки кода дописать в `[Unreleased]` (Added / Changed / Fixed).
2. Писать от продукта: не «добавил параметр», а «теперь можно X».
3. Решение неочевидно — зафиксировать причину и отвергнутое.
4. На релизе: `[Unreleased]` → версия с датой + резюме из четырёх полей.

## Проверка
Запись оправдана, если через полгода по ней отвечается: что изменилось для пользователя, почему так, где смотреть код, как было раньше.
