# Глубокий ресёрч и оркестрация субагентов (вынесено из CAMOUFOX.md)

Базовые паттерны — в `CAMOUFOX.md`. Этот док — глубина: понять тему, какой стандарт
взять и почему (при решении/выборе, не справке).

## Глубокий ресёрч — копать, а не скользить

Ответы индустрии (доки, ADR, эталонные репо) — в Camoufox ПЕРВЫМ; собственный замер —
только когда неизвестно или нужно подтвердить.

### 1. Ширина сначала, глубина потом

Норматив источников: (ядро: core.txt п.1). Сначала карта темы:

```text
5-10 web_search с РАЗНЫХ сторон (термины, англ. варианты, "best practices",
"how to", "why X not Y", сравнения) → параллельно, одним сообщением
→ отобрать кластеры: авторитетные (офиц. доки, GitHub, спеки, инженерные блоги),
  свежие, прод-проверенные
→ только ПОТОМ глубина: по 1-2 лучшим из каждого кластера
```

**Premature depth:** ныряние в один источник закрывает картину; глубина
пропорциональна задаче (сложная тема — 10+ запросов, простой факт — один).

**«Лучше перебздеть»:** сомневаешься «хватит ли?» — бери БОЛЬШЕ: нехватка = догадка,
лишний источник отсекается за секунду.

### 2. Больше источников за раз — параллельные вызовы

Все независимые вызовы — ОДНИМ сообщением (браузер ~2-5с на вызов, серия стоит как один):

```text
1-й раунд: 5-10 web_search (карта темы)
2-й раунд: 5-10 fetch_page лучших (чтение вглубь)
3-й раунд: 3-5 fetch_page/click — уточнение по находкам (feedback loop)
```

Раунды — на находках предыдущего; конец — насыщение (новые источники перестают
добавлять факты).

### 2б. Глубокий ресёрч: 30-50 источников одним вызовом (проверено 08.2026)

Батч-режим для больших тем:

```text
research(queries=[5-10 формулировок с РАЗНЫХ сторон],
         max_results_per_query=5, fetch_top=0)
    # → 25-50 уникальных URL со сниппетами одним вызовом (кэш: повтор — мгновенно)
→ batch_fetch(urls=[30-50 URL], max_chars=2000-3000, article_only=True)
    # батч ≥8 URL — параллельно (пул потоков, ~3x быстрее)
→ точечно fetch_page(url, max_chars=12000) для лучших — из кэша, мгновенно
→ findings.py add ...
```

Замер 17.08: research — 10 источников за 11.6с (кэш 0.57с); batch_fetch 10 URL — 19.5с
(последовательно ~45-55с). Кэш — SQLite `~/.cache/aggg2-camoufox/cache.db`, TTL сутки;
таймаут тула 600с хватает на 100+ URL. **Ограничитель — объём ответа**: скан с
`max_chars=2000-3000`, полный текст только для отобранных.

**Кэш:** `fetch_page`/`batch_fetch` кэшируют текст (повтор — мгновенно, без браузера;
article-режим — ключом `:article`); **web_search НЕ кэшируется** (волатильны; per-tool
TTL — tanayshah.dev/blog/per-tool-ttl-mcp-server-cache); сброс — удалить файл кэша.

### 3. Как учатся у других разработчиков (паттерн «код индустрии»)

- **Эталонные репо**: README → тесты (лучшая документация) → ранние коммиты (вся суть)
  → git log: часто редактируемые файлы = ядро (80/20).
- **Одна задача в 2-3 проектах** — сравнить подходы и trade-offs; разница = урок.
- **Реальные PR** — видно мышление: что меняют, что отвергают в ревью.
- **Issues** — «почему авторы выбрали так».
- **ADRs / RFC / design docs** (AWS, GitHub, big tech) — контекст → варианты → выбор → отвергнутое.

Искать: `web_search("github <тема> production"), "инженерный блог <тема> decision", "ADR <тема>"`.

### 4. Как выбрать стандарт («почему это стандарт»)

Критерий «так делают все» — измеряется:

- **Сколько прод-проектов используют подход** — смотреть самому в исходниках/доках.
- **Прямые сравнения** — «X vs Y», benchmark, «почему мы перешли с X на Y».
- **Авторитетность**: офиц. доки и инженерные блоги весомее личных статей; свежесть
  важнее древности.
- **Survivor bias:** популярные примеры ужасного кода — НЕ стандарт.
- **Итог выбора** = паттерн + почему победил + что отвергнуто и зачем. Без отвергнутого
  это не решение, а догадка.

### 5. Как думать как они (ментальные модели сеньоров)

- **Five Whys** — к корню решения: «почему? а почему?..» до настоящих ограничений.
- **Reversibility test** — two-way (легко отменить: библиотека, флаг) vs one-way
  (дорого: схема данных, контракт) — one-way исследовать кратно глубже.
- **Blast radius** — «что сломает изменение» ДО кода: small/medium/large/critical.
- **Systems thinking** — «вещь в её следующем большем контексте».
- **Decision journal** — как findings в research.db: решение + причина + ожидаемый результат.

## Оркестрация большого ресёрча — субагенты по под-вопросам

Для больших тем один агент упирается в контекст и время. Паттерн индустрии
(LangChain deepagents, fast.io, arXiv 2506.18096): decompose → субагенты → синтез.

```text
1. DECOMPOSE: 5-15 под-вопросов (fast.io: меньше — мелко, больше — теряется нить).
   План — в отчёт (docs/research/).
2. СУБАГЕНТЫ: на каждый под-вопрос — task-субагент, ПАРАЛЛЕЛЬНО. Каждому:
   под-вопрос + «web_search → fetch первоисточников → вывод с URL; верни компактное
   резюме». Изолированный контекст — не тащит весь ресёрч.
3. СИНТЕЗ: собрать резюме, сверить противоречия, каждое утверждение — с URL.
4. ОТЧЁТ: docs/research/<дата>-<тема>.md + findings.py add (--source на отчёт,
   --related на связанные находки).
```

Не дробить мелкое (справка — 1 субагент, сравнение — 2-3, обзор индустрии — 5-15);
каждый субагент — узкий (один под-вопрос).
